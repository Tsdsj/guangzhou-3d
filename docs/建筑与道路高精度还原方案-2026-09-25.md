# 广州三维城市：建筑外墙与道路高精度还原方案

日期：2026-09-25。状态：调研与方案草案，尚未进入实现。

约束：仅使用免费公开数据；沿用当前项目；不采购数据，不以现场测绘或付费服务为前提。免费公开仍需满足具体数据的使用与再发布许可。人工整理、建模、算力和存储并不因此免费。

## 1. 结论与目标边界

建议采用 **“开放数据补齐城市底图 + 有证据的逐栋、逐立面还原 + 道路拓扑与横断面重建 + 分块加载”** 的路线。保留 Three.js、现有场景和氛围渲染，不先更换引擎。

当前主要瓶颈是事实数据不足及其表达方式，而不是面数不足。单纯提高细分、照片分辨率、反射或 AI 生成细节，会提高写实感，但不会自然提高与真实广州的一致性。

必须区分三个目标：

| 目标 | 本项目应如何理解 | 免费公开数据下的判断 |
| --- | --- | --- |
| 1:1 比例 | 米制尺寸、坐标与尺度一致 | 可建立统一标准，但不代表源数据准确 |
| 外观与结构还原 | 具体建筑的体量、门窗、柱廊、材质，具体道路的断面、路口、上下层关系一致 | 资料充分的对象可显著接近；覆盖范围取决于证据 |
| 测绘级精度 | 对绝对位置、尺寸与高程给出可检验误差 | 当前数据不足；没有独立控制点/测量资料时不能承诺厘米或分米级精度 |

推荐交付目标：全范围逐步提高真实轮廓覆盖率和路网完整性；重点街段按每栋建筑、每个立面和每个路口核验；没有证据的部分保留低细节表达并标明推断。先做样板，不能提前承诺约 127.6 km² 全范围的外墙和道路全部 1:1。

## 2. 本轮核实的项目现状

### 2.1 架构与可复用部分

- 纯静态站点，原生 ES Modules + import map；Three.js 0.185.1，依赖已裁剪到 vendor。
- 数据链路：Overpass → `data/raw/` → `tools/build-city.mjs` → 元数据与两个 gzip 二进制包 → 浏览器装配。
- 已有建筑轮廓挤出、分块合批、程序化立面、骑楼与屋顶构件、道路条带、桥梁结构、地形、水系、交通和树木 LOD。
- 当前产物首屏数据 5,167,508 字节，植被包 1,976,665 字节；合计约 7.14 MB（十进制）。
- 已有 Git、数据 schema、确定性构建快照测试。2026-09-24 的旧评估报告中“没有 Git/测试”等判断已经过时，不能直接作为本次计划起点。
- 本轮在后台浏览器打开当前 localhost:5173，切换并查看了沙面街景的实际渲染，观察到程序化重复窗型和风格化街道。这是现状观察，不是精度验收或性能基准。

| 来源 | 能解决的问题 | 本轮已确认与边界 | 建议 |
| --- | --- | --- | --- |
| OpenStreetMap | 道路连接、建筑轮廓/部件、部分高度和道路属性 | 当前项目已有快照；本地属性缺失率已统计 | 主干来源，先把未利用的数据接进来 |

| Wikimedia Commons | 具体建筑立面、屋顶、门窗与材质参考 | 已找到沙面建筑分类与多栋照片目录；每张照片须分别检查许可、日期、朝向和遮挡 | 优先作为可核对的逐栋参考；确认允许改编后才烘焙入纹理 |

| 政府开放数据、公开工程/保护资料 | 楼高、建筑身份、道路断面、桥型和历史建筑细节 | 广州有实景三维建设，但本轮未找到可直接免费再发布的全城精细模型下载证据 | 逐项审查具体资料；“政府已有数据”不等于“公众可下载复用” |
| GlobalBuildingAtlas | 更多建筑轮廓及推断高度/LoD1 | 当前官方说明将 ODbL 轮廓与 CC BY-NC 4.0 的部分轮廓、LoD1、高度产品拆分 | 不默认并入公开发布主数据；用途匹配且许可兼容后才能进入独立候选方案 |

本轮没有下载或融合上述外部建筑数据，没有核定任何样区的全立面照片覆盖率。它们是已核查来源说明的候选，不是已经验证可直接交付的数据包。

免费数据选择原则：

1. 不以地图网页能看到、API 有免费额度、图片可搜索到作为可离线提取并再发布的依据。商业地图和街景不作为默认纹理库。
2. 记录 source URL、许可、版本、获取日期、观测日期、坐标系、原始 ID 和修改记录。抓取时间不能代替拍摄或测绘时间。
3. 对同一栋楼不直接拼接多源几何：先匹配，检查 footprint 与 roofprint 差别、建筑部件与整体差别、年份差别，再选用字段。
4. 开放数据只能提高机会，不能保证有四面立面、立交纵断面或最新店招。获取不到的字段保持未知。

## 4. 三条技术路线的取舍

| 路线 | 优点 | 对 1:1 的限制 | 结论 |
| --- | --- | --- | --- |
| 继续增强全城程序化生成 | 上手快、资产轻、复用现有代码多 | 原始尺寸/照片缺失时，细节仍是猜测 | 用于远景和未覆盖区 |
| 开放数据融合 + 重点区域逐栋精修 | 保留现有系统；成果可追溯；能逐街区扩展 | 数据整理与人工标注是持续成本，资料薄弱区域需降级 | 推荐主线 |
| 公开照片摄影测量/NeRF/3DGS | 对具备重叠多视角影像的局部可能有很强照片感 | 不会补足未拍摄表面；散乱旅游照片常缺尺度、重叠和一致光照；道路语义、编辑和动态昼夜还需处理 | 只作资料满足条件时的局部实验，不作为全城前提 |

不建议第一步改成 Cesium 或其他整套引擎。引擎替换无法补足立面事实；当前 Three.js 足以先验证高精度资产是否能显著改善场景。若之后确实需要标准化大规模瓦片，可评估支持 Three.js 的 [3DTilesRendererJS](https://github.com/NASA-AMMOS/3DTilesRendererJS)，但需验证与当前版本及渲染效果的兼容性。

## 5. 建筑还原方案

### 5.1 先提高“真实建筑对应率”

在样区比较 OSM 与 Overture：按空间重叠、中心距离、形状、名称与部件关系生成候选匹配；一对多、多对一和冲突对象进入人工核对，不自动按单一阈值替换。

保留已有明确可靠的轮廓。新增真实轮廓时，同步清除覆盖范围内的程序化填充建筑和附属构件，并更新占用区域。只隐藏主体会残留浮空水箱、招牌或骑楼构件。

建立稳定 buildingId/partId；轮廓更新后仍能关联人工制作的立面。填充体块、真实轮廓、照片复原资产分开计数。真实轮廓只证明平面依据，不能自动把该楼的高度与外墙也标成真实。

### 5.2 将每栋楼拆成体量、立面与构件

建议数据层次：

```text
Building：身份、轮廓、基底、高度、屋顶、来源
  ├─ Part：裙房、塔楼、退台、架空段
  ├─ Facade：朝向、局部坐标、照片、楼层线、开间
  │    ├─ Opening：门、窗、入口、洞口
  │    └─ Component：阳台、廊柱、檐口、雨棚、空调位
  └─ Evidence：字段来源、日期、可信等级、未知项
```

Facade ID 应关联规范化边/面及其空间位置，不能只用会随多边形简化变化的边序号。

普通建筑采用“明确参数的模块化建模”；异形地标、历史建筑采用单体 GLB。程序化 shader 继续服务远景与低证据建筑，已核实的立面参数优先覆盖随机参数。

### 5.3 照片到外墙的具体流程

1. 对应建筑身份与朝向，建立逐面资料表；先确认同一时期，避免把改造前后立面拼在一起。
2. 对平面墙做透视校正；弧面、凸出阳台和深柱廊单独建模，不能整面一次拉平。
3. 有可靠尺寸时定标；否则记录相对比例和尺寸估计区间。不能仅凭一张照片推定精确深度。
4. 标注楼层线、每层开间、入口位置、窗型、窗墙比、阳台和屋顶轮廓。AI 可辅助标注候选，由人工核对。
5. 影响轮廓、遮挡和近景视差的部分做真实几何：门窗洞口、窗台、阳台、柱廊、檐口、退台；小纹理以材质表达。
6. 纹理制作尽量去除照片中的固定光照、行人和车辆；无法消除的树木遮挡不能复制成永久墙面。玻璃反射、窗内亮灯与墙面颜色分离，以适配现有昼夜系统。
7. 对未知背面保留低细节并登记缺证，不能镜像正面后称四面还原。

AI 生成的纹样、补洞照片和单图生成模型，只能算视觉推断；不进入真实性覆盖率。遮挡区生成结果也需要相同标记。

## 6. 道路结构还原方案

道路按“网络连接 → 平面边界 → 横断面 → 路口 → 纵断面/桥隧”推进，最后再做沥青纹理与灯光。

### 6.1 补齐源数据与真实拓扑

- 保留 OSM node/way/relation 的 ID、way 节点序列和关系成员 ref/type/role；数据原始格式需要升级。
- 纳入人行道、自行车道、台阶、穿楼通道、过街点、道路面、交通岛和信号灯；对于 area:highway，要进入道路面处理而不只当普通地块。
- 获取转向限制和明确的车道连接；模型的转向箭头、车流路径使用同一份连接数据。
- 共享节点是重要依据，仍结合桥隧、层级和通行方式判断，不能仅因二维交叉就连通。
- 对未绘制的小路和出口显式保留缺口状态；网络形式上连通不等于位置和路权都真实。

OSM 已定义 [车道语义](https://wiki.openstreetmap.org/wiki/Key:lanes)、[转向车道](https://wiki.openstreetmap.org/wiki/Key:turn) 与 [转向限制关系](https://wiki.openstreetmap.org/wiki/Relation:restriction)，但有字段定义不代表广州对应位置已被填写。

### 6.2 从等宽条带改为沿程横断面

每个道路区段按里程保存宽度变化与左右组成，例如：人行道 / 非机动车道 / 机动车道 / 分隔带 / 对向车道 / 人行道。示例只定义结构，不预设真实尺寸。

- 分别记录 forward/backward 的车道数量、每车道宽度、用途和转向。
- 支持转弯车道渐变、公交港湾、停车带、中央开口和道路收窄。
- 使用可靠边界时直接生成路面；只有中心线时允许估计断面，但标为 inferred。
- 路缘石、人行道高差、隔离带、坡道做显式几何，贴地与建筑入口保持一致。
- 路口建立共享面域，裁剪各进口道，生成转角、导流岛和车道连接曲线，消除道路条带叠压造成的假路口。
- 标线使用有方向与位置的数据对象驱动 decal/mesh/shader；着色器负责画法，不再决定真实世界哪里应该有斑马线。

### 6.3 桥梁、隧道和高程

保留 layer 的相对层级含义。只有查到公开工程资料或可核验高程时才赋予确定高度；其余给估计值与来源。

需要分别处理桥面纵坡、匝道接入、桥下净空、地面辅路、隧道入口及连接。隧道内部可在首期简化，但不能把隧道数据删掉造成道路网络断裂。

当前 DEM 适合远山和宏观地形，不足以确定路拱、缘石和匝道精确高程。也不能把树冠/楼顶造成的 DSM 高程直接贴给道路。

## 7. 坐标、运行时与资产组织

### 7.1 坐标与误差

源数据保留其原始 CRS 和垂直基准。渲染使用统一局部米制坐标；对当前固定经纬度比例投影与标准地理变换做对照，再决定迁移到局部 ENU 或适合样区的投影。

混入不同坐标系或地图偏移坐标的数据时先转换并用控制点复核，不能靠目测平移。明确区分绝对海拔、相对地面高度和当前渲染零点。

误差分开记录：源数据误差、配准误差、简化误差、量化误差、人工重建误差。减少压缩或提高 Float 精度只能降低后几项，不能制造源数据精度。

### 7.2 三层运行时表示

| 范围 | 表示 | 原则 |
| --- | --- | --- |
| 城市远景 | 当前轻量体量与程序化材质 | 保留原有加载和航拍体验 |
| 街区中景 | 校正体量、屋顶、简化立面 | 逐块加载，合批与共享材质 |
| 街道近景 | 逐面纹理、凹凸构件、路缘与标线 | 仅加载可见邻域；按屏幕误差切换细节 |

第一版可从 250–500 m 级街区资产包试验，根据实际密度调整。新旧层由相同实体 ID 控制替换，不能叠出两栋楼，也不能因为精细包加载失败留下空洞。

建议 GLB + KTX2/Basis 纹理，并按实测选择 meshopt 压缩。Three.js 官方加载器支持相关机制，但当前 vendor 中未找到 GLTFLoader/KTX2Loader/解码器，需要后续补入与本项目版本匹配的最小依赖及许可文件；不能假设已安装。见 [GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)、[KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html)。

建立请求去重、优先级、取消、缓存与显存释放；离开区域时回收纹理、几何和 image bitmap。首个样板先用简单的静态 manifest + GLB 分块验证，再评估是否需要 3D Tiles，避免提前引入复杂平台。

## 8. 样板与实施阶段

建议首期覆盖两类问题，避免只选漂亮地标掩盖道路能力不足：

- **建筑样板候选：沙面大街约 300–500 m**，计划选 10–20 栋有明确身份与可用照片的建筑；先做到 3 栋资料最齐的逐面样件，再扩展。已找到公开照片目录，但最终范围必须由逐栋照片盘点决定。
- **道路样板候选：花城大道约 500–800 m 的路段和 2 个相邻路口**，要求包含方向差异或主辅路结构；是否纳入桥隧连接由资料决定。沙面不能覆盖复杂机动车路口的验收。

候选街段若资料不足，应缩短或改选，不为了凑数量编造立面和道路尺寸。恩宁路可作为后续骑楼样板，需先验证资料充分性。

| 阶段 | 交付 | 通过条件 | 粗略工作量 |
| --- | --- | --- | --- |
| P0 数据与精度可行性 | 样区裁剪对比、逐栋/逐面照片清单、道路属性清单、坐标与许可记录 | 至少有可制作的 3 栋建筑样件与可核对的道路/路口；明确未知项和能声称的精度 | 2–4 人日 |
| P1 数据底座与事实优先级 | 稳定 ID、来源/日期/可信度、完整拓扑、样区真实轮廓替换填充 | 不重复、不误删部件；有证据字段不被模板覆盖；样区统计可追溯 | 4–7 人日 |
| P2 可查看的质量样板 | 3 栋逐面建筑、1 个路口的独立可浏览演示及原图对照 | 先确认实际模型效果、几何层次和缺证表达，再推广 | 5–9 人日 |
| P3 正式集成与样板扩展 | 10–20 栋建筑候选、500–800 m 道路候选、2 个路口、分块加载 | 达到下节验收；原有航拍与其他街区不回退 | 8–15 人日 |
| P4 按资料覆盖逐街区扩展 | 可持续的数据更新/资产制作清单 | 以新核实的建筑、立面面积、道路长度计进度 | 由 P3 实测吞吐估算 |

P0–P3 约 19–35 人日是用于排期讨论的估算，不是工期承诺；假设具备 GIS/Three.js 工程和基本建筑建模能力、许可明确、照片可用。不包含大量手工绘制缺失资料、复杂地标雕刻和等待外部数据。P0 完成后应根据每栋处理时间重估，不能拿样板成本线性推算全城。

P2 演示与正式场景隔离，保留原始照片、标注和模型作为后续验收依据；质量方向确认前不大范围改动现有场景。

## 9. 验收标准

### 9.1 先建立证据，再设精度数字

每个样板明确“采用哪个日期的现实”。对不同年份冲突资料记录取舍。相同素材不能既作为唯一建模输入，又作为独立测量真值。

| 维度 | 建议验收方式 |
| --- | --- |
| 真实对象对应 | 样板逐栋 ID、名称/位置、轮廓、部件可追溯；精细区域不混入未说明的虚构建筑 |
| 建筑外观 | 对有清楚证据的立面逐项核对楼层数、开间数、入口、窗型、阳台、柱廊与屋顶轮廓；这些离散结构不应出现错项 |
| 尺寸 | 只有独立且精度足够的参考时，才采用指标，例如主体尺寸相对误差不超过 2–5%、关键构件偏差不超过 0.1–0.3 m；这些是候选验收阈值，P0 后校准，不是当前可达承诺 |
| 绝对位置与高程 | 有控制点时统计 RMSE、P95 和最大偏差；没有控制点则标“未验证”，不得用截图观感代替 |
| 道路拓扑 | 样板内入口、出口、单行方向、主辅路、桥隧上下层与已证实的转向限制一致；不存在假连接、断口和穿层 |
| 道路几何 | 有可量测依据时检查边界、路口形状、车道宽度与纵坡；无依据的米数保持估计标签 |
| 立面覆盖 | 分别报已核实临街立面面积/总临街立面面积、已核实全外墙面积/总外墙面积；未核实背面不能算完成 |
| 运行体验 | 固定硬件、浏览器、分辨率和画质；记录加载字节、帧时中位数/P95、内存、显存估计和加载峰值；连续漫游观察释放与切换 |

性能初始目标可设桌面 1440×900 精细样区稳定 45–60 fps，移动设备使用简化层争取 30 fps；均需另行实测，不能引用旧报告证明新资产已达标。基础首屏原则上维持约 7 MB 的量级，精细包按需下载；每块大小在 P2 测量后定额。

### 9.2 必须补充的验证

- 数据：多源匹配冲突、单位解析、CRS、一楼多部件、照片授权与失效链接。
- 几何：建筑与道路侵占、自交、路口接缝、相邻块裂缝、重复建筑和悬空构件。
- 路网：单行方向、双向不等车道、桥隧分层、匝道和断头路；车流与道路共用连接。
- 视觉：固定日间中性光照与相机，对照照片；再验证傍晚、夜间和雨天。不能依靠雾和夜景掩盖建模差异。
- 实际操作：沿街移动、近距离观察门窗/柱廊、穿越路口、从近景退到航拍、快速切场景；验证加载失败回退和资源释放。
- 回归：复用现有全部场景进行加载与截图检查，对发生变化的区域重点验收，不用新模型遮盖旧场景回退。

原有哈希快照继续保护构建可重复性，但“fill 必须很多”的断言需要随目标调整。测试结果不代替真实地理对照。

## 10. 优先级与下一步建议

首要顺序是：**数据覆盖与来源 → 真实轮廓与体量 → 道路网络和断面 → 逐面门窗与构件 → 材质细节 → 扩大覆盖范围。**

不优先做全城统一换高清纹理、增加随机空调/店招、继续堆积填充建筑，或全面替换引擎。这些都不能解决当前最大的真实性缺口。

建议后续首先执行 P0，交付可核查的样区资料与覆盖图；只有证明免费数据足以支撑样板，才进入数据管线与模型实现。若照片或道路尺寸不足，保留仅用免费公开数据的约束，缩小高精度范围并清楚说明未验证部分。

本轮完成：代码与文档调查、本地原始数据统计、当前沙面街景观察、官方外部来源核查，以及本方案。未修改产品代码、未刷新城市数据、未运行建模任务、未对新精度和新性能作完成声明。
